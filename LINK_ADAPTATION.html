一、调研：业界怎么做 L1 仿真

完整链路级仿真（Sionna PHY、MATLAB 5G Toolbox）跑的是这一整条链：

比特源→ CRC→ LDPC 编码→ 速率匹配→ QAM 映射→ 预编码→ 信道→ MIMO 检测→ 软解调 LLR→ LDPC 译码→ CRC 校验

加粗的三段 superwireless 本来就有。缺的是两头的编解码与调制映射， 它们决定了 BLER 与吞吐。

但做系统级仿真时，业界并不跑这整条链。 3GPP 的评估方法学、ns-3、Vienna 模拟器走的都是链路到系统映射： 把逐 RE 的 SINR 矢量压成一个有效 SINR，再查 BLER。

原因很实际：每个样本跑一遍 LDPC 译码要几百毫秒， 而蒙特卡洛动辄几百上千个样本、还要扫多个工作点。链路到系统映射把这一步 变成查表，快三四个数量级，代价是 BLER 从"实测"降级为"映射"。

还有一个现实约束：Sionna 2.0 把包拆开了，本机装的 sionna-rt 只有射线追踪，PHY 层在另一个包里且依赖 TensorFlow（约 600 MB，且与现有 numpy/scipy/torch 有版本冲突风险）。 为了 BLER 引入整个 TF 栈，代价远大于收益。

二、香农谱效不是吞吐，差多少

ds.link() 给的 SE = Σ log2(1+SINR) 是香农上界。 真实系统达不到，差距来自三项，每一项都可量化。

损失一：调制受限 —— 精确可算

星座点数摆在那里。方形 M-QAM 的对称信息率（约束容量）用 Gauss-Hermite 求积精确计算：

SNR香农QPSK16QAM64QAM256QAM
−10 dB0.1380.1370.1370.1370.137
0 dB1.0000.9720.9900.9920.992
10 dB3.4591.9943.1643.2693.284
20 dB6.6582.0004.0005.8016.257
30 dB9.9672.0004.0006.0007.995

20 dB 时香农说 6.66 bit/s/Hz，64QAM 最多只能给 5.80。 低信噪比处两者重合，高信噪比处饱和到 log2(M) —— 三条性质都在测试里核过。

实现时踩的坑：sigma 定义差一倍就是 3 dB。 约定复符号 E|x|²=1、复噪声 E|n|²=1/γ，折到实维并把星座归一化到单位能量后， 噪声方差正好是 1/γ，所以 sigma = 1/sqrt(γ)—— 写成 1/sqrt(2γ) 会整体多给 3 dB。

而且看起来完全正常：曲线形状对、饱和值对， 只是位置平移。抓它的唯一办法是低信噪比处对香农——约束容量在 γ→0 时 必须与 log2(1+γ) 重合。这条自检已写进测试。

损失二：码率离散

38.214 的 MCS 表只有 29 档（表 1）或 28 档（表 2）。实际码率总是落在 需要的码率之下，用不满。

损失三：有限码长 + 实现损失

LDPC 距容量约 1~2 dB；TB 还要按 38.212 切成多个码块， 任一块错则整块错——273 PRB 的 TB 有二十多个码块。

三项加起来的实测差距（21 小区 64T 100MHz，200 样本）：

香农谱效 69.2 bit/s/Hz
实际谱效（MCS 表 1） 22.3 bit/s/Hz — 32%

低信噪比处达成率 70~77%，高信噪比处掉到 38% —— 后者不是信道问题， 是 MCS 表封顶（下一节有证据）。

三、哪些是算的、哪些是模型

必须分清，否则会把模型当测量用。

部分性质依据
QAM 约束容量精确计算 Gauss-Hermite 求积；可对香农上界、饱和值、低信噪比重合三重自检
有效 SINR（MIESM/EESM）标准口径 互信息平均 / 指数平均。默认 MIESM，不需要逐 MCS 标定 β
MCS / CQI 表标准查表 TS 38.214 V17.5.0 Table 5.1.3.1-1/-2、5.2.2.1-2/-3，从 PDF 机械解析
TBS标准算法 38.214 §5.1.3.2，查表分支与量化分支都实现
码块分段标准算法 38.212 §5.2.2，BG1/BG2 选择与分段
BLER（表 1/2）分析模型 有限码长形状 + 可配实现损失。没有 3GPP 参考曲线兜底
BLER（表 3）用户曲线 28 档 MCS × NewTx/ReTx，共 56 条、1824 点；不是 3GPP 标准曲线

表格的自检

MCS/CQI 表有一条内蕴冗余关系：SE == q_m × R / 1024。 抄错一个数就对不上。87 行全部核过——这是上次 CDL 表事故之后定的规矩： 一份查表值必须有第二条独立路径核对。

公开 NR 链路级曲线的常见量级是 MCS0 约 −5~−7 dB、MCS28 约 20~23 dB， 模型落在区间内。距香农的差距随码率上升（1.3 → 3.1 dB），符合定性预期。

MCS10 的门限比 MCS9 低 0.31 dB —— 这是标准表本身的设计，不是缺陷。 标准在调制切换点上故意让 SE 重叠：MCS9 是 QPSK R=0.663（SE 1.3262）， MCS10 是 16QAM R=0.332（SE 1.3281）——同样的 SE，后者码率低得多，所以更省信噪比。

所以单调性判据只能在同一调制阶数内部要求。 一开始整体判单调，把这两点误报成了模型失败。

新增表 3：company_20b_256qam。公司侧提供的 28 档 MCS、 NewTx/ReTx 两套解调曲线已经作为独立后端接入。以 MCS 15 为例：64QAM， NewTx R=0.650 的 10% BLER 门限为 14.042 dB，ReTx R=0.333 为 7.743 dB。数据所有者已确认原始标签 Es/No 就是经典 MMSE 接收机的 SINR；TB/CB、块长、信道模型、MIMO 层数和译码器细节暂不参数化。

曲线逐点哈希、56 条覆盖、横轴递增、BLER 单调下降、 10% 门限覆盖都会自检。范围外保守钳位，不外推假尾部。

TDD AMC 已接通。输入 CQI 后，先按谱效映射公司表初始 MCS， 再取该 MCS 的 NewTx 目标 BLER SINR 门限。BF Gain 逐 RB、逐流定义为同一信道、 CSI、rank、功率、干扰和经典 MMSE 接收机下 SINR_SVD - SINR_PMI；叠加后对全部 RB×流在 dB 域做算术平均， 重新映射 MCS，最后在 MCS 域加 OLLA、严格 floor 并钳位到 0..27。

CQI=0 不调度。默认 10% 目标下 ACK +0.1、 NACK -0.9 MCS，反馈只改变下一时刻 OLLA。接口返回初始门限、逐流 PMI/SVD SINR、 BF Gain、用户 SINR、取整前后 MCS 和最终 BLER，不隐藏中间口径。

均值提升 23%，而边缘用户几乎不变——边缘用户本来就用不到高阶调制， 这一条本身就是有用的结论。sw_throughput 检测到大量样本封顶时会主动提示。

5% 边缘用户吞吐是 3GPP 评估里的公平性指标，比均值更能说明问题。 上面这例：均值涨 23%，边缘用户涨 0.3% —— 只看均值会得出"256QAM 大幅改善"的结论， 看了边缘用户才知道改善的是谁。

六、性能：并行生成

实测单样本耗时相差 85 倍，主导因素是小区数与天线×RB。

配置毫秒/样本200 样本串行
单小区 32T 20MHz244.7 s
21 小区 32T 20MHz41082 s
单小区 64T 100MHz19138 s
21 小区 64T 100MHz2054411 s

多小区贵 11~17 倍——要算几何 SINR 与逐干扰小区的贡献。 workers="auto" 按预估耗时自动决定（四个标定点误差都在 ±30% 内）。

第一版并行只有 1.34 倍加速。原因是每个 worker 各自开满 CPU 核数的 BLAS 线程：20 个 worker × 20 线程抢 20 个核， 上下文切换吃掉了全部收益。

修法是在 import numpy 之前把 OMP_NUM_THREADS 等设成 1。进程级并行 + 单线程 BLAS 是数值计算里的标准组合，但很容易漏。修完拿到应有的加速：

场景串行并行加速
21 小区 32T，120 样本65.4 s23.8 s（10 进程）2.75×
21 小区 64T 100MHz，200 样本~842 s（预估）245.7 s（20 进程）3.4×

没到 20 倍——内存带宽是瓶颈，20 个进程同时搬 273×64 的复数数组。 3.4 倍是实测值，不做更高的宣称。

并行结果与串行不是同一批样本。分块靠给每块不同的 seed（实测 ue_seed_offset 对撒点毫无影响，只有 seed 真正换随机流）。所以串行 seed=S 跑 N 个 vs 并行 seed=S..S+W−1 各跑 N/W 个，统计等价、各自可复现，但逐样本不同。

实测 SINR 分布 KS 检验 p=0.90，统计上相容。 这一点写进摘要的 parallel 块，免得"换了 workers 结果对不上" 变成隐形陷阱。配对比较不受影响——两臂本来就要用同一个数据集。

多进程在某些宿主里起不来（Windows spawn 需要可导入的 __main__， REPL 和 python -c 里没有）。这时降级串行并把原因记进摘要， 不让整次生成失败——但也不静默，否则用户会纳闷为什么没变快。

5 个 BLER / 吞吐 / TDD AMC MCP 工具（当前总数 30）

工具作用

八、已知局限

局限为什么怎么应对
BLER 证据依赖后端 表 1/2 是分析模型；表 3 是经典 MMSE 接收机的用户 SINR 曲线，其他维度暂不参数化 结果保留 bler_source、接收机与横轴口径；不额外推断块长等影响
EESM 的 β 未逐 MCS 标定 β 要拿自己的链路级曲线标定 默认走 MIESM（不需要 β）；用 EESM 请自行标定后覆盖
HARQ 仍有简化 表 1/2 假设每次同 BLER；表 3 首传用 NewTx、后续复用唯一一条 ReTx 曲线 返回 harq_model，不把多次 ReTx 复用藏起来
没有 L2 调度器 多用户调度、MU-MIMO 配对、业务模型都不在范围内 当前是单用户链路视角；多用户要另建一层
并行只有 3.4 倍 内存带宽瓶颈，不是 CPU 瓶颈 如实报实测值。更高加速要改数据布局，收益不确定
耗时预估误差 ±30% 四点标定的经验式，机器不同会偏 只用于调度决策与提示，不用于承诺

这一轮之后，"我提一个算法思路 → 在可信信道上跑蒙特卡洛 → 拿到经得起推敲的结论" 这条路上，结论可以是 Mbps 而不只是 bit/s/Hz 了。 差别在于前者是系统真能拿到的，后者是理论上界。
