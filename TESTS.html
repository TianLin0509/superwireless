先说结论：这个数字本身是个弱指标。 它是"实际执行了多少条断言"， 一个 for 循环就能凭空加 26 条。真正有价值的不是 635 这个数， 而是其中哪几条是从真实事故里长出来的——本页第三节列了 8 条。

一、它其实是什么：一个 8 行的小函数

没有 pytest，没有框架。整个测试体系的核心就是这么一个函数， 每个测试文件开头都抄了一份：

FAILED: list[str] = []

def check(cond: bool, label: str) -> None:
    print(("  PASS  " if cond else "  FAIL  ") + label)
    if not cond:
        FAILED.append(label)

"635 项"就是这个函数被调用了 635 次，每次打印一行 PASS 或 FAIL。 跑完统计 FAILED 列表，非空就 sys.exit(1)。

一条 check 长这样

# 物理自检：IoT 公式必须和定义式逐位相等
check(worst < 1e-9,
  "IoT = SIR/(SIR-SINR) 与 (I+N)/N 一致")

跑出来是一行 PASS IoT = SIR/(SIR-SINR)…

为什么不用 pytest

因为这些"测试"多数在打印物理量：偏差多少 dB、中位数多少、 分布长什么样。pytest 默认吞掉 stdout，而这里输出本身就是给人看的证据。

代价是没有 -k 筛选、没有并行、没有覆盖率统计。

三、拦住过什么：8 个真实事故

下面每一条都真的发生过，而且都有一个共同点： 数值看起来完全正常。这才是要测试的理由——能报错的 bug 不需要测试来抓。

1. 门 3 用错了判决检验

是什么：PairedResult.significant 只看配对 t 检验，而文档写着「两检验冲突时以 Wilcoxon 为准」。

有多隐蔽：回归样本 n=8：t 检验 p=0.044（显著）、Wilcoxon p=0.109（不显著）。按承诺该拦，实际放行了。

承诺的判据和代码用的判据是两回事 —— 这比判据宽松更危险
守它的 check：test_gates 6.5

2. QAM 互信息整体偏 3 dB

是什么：sigma 写成 1/√(2γ) 而不是 1/√γ。

有多隐蔽：曲线形状全对、饱和值全对，只是整条平移 3 dB —— 肉眼完全看不出。抓它的唯一办法是低信噪比处对香农：约束容量在 γ→0 时必须与 log2(1+γ) 重合。

「看起来完全正常」的错误只能靠解析自检抓
守它的 check：test_linkadapt 1

3. 多小区配了 21 个小区，干扰根本没进 SINR

是什么：缺 bs_panel 时 ChannelHub 建不出 DFT 码本，静默走兜底：sir_dB=49.9 哨兵、sinr_dB=snr_dB。

有多隐蔽：同配置修复前后 SINR 中位数 35.7 → 18.1 dB。这条路径不报错、不告警、不打日志。

静默兜底最致命 —— 数值看着完全正常，结论全错
守它的 check：validate 门 1

4. CDL 角度表和 38.901 对不上

是什么：三张表都标着「TS 38.901 Table 7.7.1-x」，时延与功率对，角度列从中段起不是。

有多隐蔽：CDL-C 有 23/24 个簇有出入、占总功率 93.8%，按 Annex A.1 算 ASA 偏 14.5°、ASD 偏 7.1°。

「标着标准号」不等于「是标准值」，得逐字核对
守它的 check：test_gates 1

5. 测试自己把乱码吞掉了，照样报通过

是什么：子进程按 GBK 输出中文，父进程按 UTF-8 解码，errors="replace" 把它换成 U+FFFD。

有多隐蔽：测试通过，等父进程把 U+FFFD 打到 GBK 控制台时才炸，而且报的是父进程的错。

兜底参数会把失败伪装成成功 —— 测试本身也需要被怀疑
守它的 check：test_e2e 9

6. 文档里的「19 项体检」是编的

是什么：这句话在 README / SKILL.md / 两份 HTML 里写了八处。

有多隐蔽：而代码从第一版起就只有 16 项；CAPABILITIES.html 另一处写着 12 项。数字凭印象写的，从没对过账。

加了正则 guard 后当场又抓出第二处
守它的 check：test_interference 10

7. preset 写死 bs_panel 让天线覆盖失效

是什么：用户传 bs_antenna="4T4R"，num_bs_tx_ant 变成 4，而 bs_panel 还是 [8,4,2]（64 口）。

有多隐蔽：两者矛盾，生成出来的 BS_ant 不是 4。这是本次改动引入的，提交前被当场拦下。

测试的价值不只是守旧代码，更是守住今天刚写的
守它的 check：test_mcp_server 5

8. 350 km/h 的高铁场景，多普勒报 0.0 Hz

是什么：doppler_hz 来自同一 UE 相邻样本之间的位移，每个 UE 只有 1 个样本时没有位移可算。

有多隐蔽：num_samples=21 报 0.0 Hz，num_samples=42 报 817.94 Hz。而 num_samples 恰好等于 num_ues 是很自然的写法。

现在自动补够样本并写进报告 —— 补，但不静默地补
守它的 check：test_interference 8.5

注意第 5 条和第 7 条。第 5 条是测试自己出的错——它把乱码 吞成 U+FFFD 然后报"通过"；第 7 条是今天刚写的代码被当场拦下。

测试不是只用来守老代码的护栏，它同时是"我这次改动有没有踩到自己"的 即时反馈。这次改默认阵列，两分钟内就被告知"你把 4T4R 覆盖弄坏了"。

四、三类 check，价值差很远

最硬
物理自检——能手推证明的等式，偏差只能是机器精度。
IoT 公式对定义式：偏差 1.1×10−14 dB · QAM 约束容量在 γ→0 时对香农 · 38.214 表内蕴关系 SE == q_m·R/1024 逐行核 87 行 · 负载 ↔ IoT 往返一致
这类 check 一旦红，一定是代码错了，不可能是"容差没调好"。
很硬
回归测试——从真实事故里长出来的，带着当时的具体数据。
门 3 那组 n=8 的样本（t p=0.044 / Wilcoxon p=0.109）· 探测模式在 num_ofdm_symbols=1 处的悬崖 · 4T4R 覆盖
这类 check 的注释里都写着"别删"——删掉等于把学费白交。
较软
契约与形状检查——数量最多、单条价值最低。
每个预设有 group/label/summary · 引擎清单恒为三条 · 返回的字典里有哪些键
635 里被循环放大的主要是这一类。它们防的是"手滑漏填"， 不是"物理算错"。

五、它证明不了什么

测试证明的是「自洽」和「没漂移」，不是「物理对」。 两者差得很远。

  • BLER 是模型，不是实测。 分析模型没有 3GPP 参考曲线兜底； 用户提供的公司曲线虽然贴近真实接收机，但也不是标准表、没被独立核对过。 测试只能查它单调、覆盖全 MCS、哈希没变——查不了它准不准。
  • 阵元方向图是 3GPP 式参数化模型（element_pattern_is_measured: false）， 不是实测 Jones 方向图。测试保证这个标志不被误报成实测，仅此而已。
  • 没有 CI。 ChannelHub 是私有依赖，云端拿不到，所以这 635 条 只在这台机器上跑过。"在我这儿是绿的"这句话的全部含金量就到这里。
  • 覆盖是偏的。 射线追踪只有 8 条（因为慢且依赖大）， L2 调度、MU-MIMO 配对一条都没有——因为那些功能还不存在。 测试数只反映已有功能的密度，不反映功能的完整度。
  • 数字会通胀。 想让它变成 800 很容易，多写两个 for 就行。 所以本页开头那句要再说一遍：看哪几条，别看几条。
