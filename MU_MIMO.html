MU-MIMO 算法流程

等效信道 → 配对 → 多用户预编码 → 功率分配 → 逐用户 SINR

"不配对"反而最高，这不是 bug。 64 端口只服务 12 个用户时空间自由度富余， ZF 撑得住 12 条流。配对真正开始起作用是在用户数逼近端口数、 或者 CSI 有误差的时候——那时把强相关用户塞进同一组，ZF 会互相把功率吃光。 所以这张表不能读成"配对没用"，只能读成"这个工况下自由度还没用完"。

一、算法流程

1

逐用户等效信道

每个用户的下行信道是 H_u^H（[UE_ant, BS_ant]）。 在每个 RB 上做 SVD，取前 S 个左奇异向量当接收合并权：

H_u^H = U Σ V^H → 等效行向量 h̃_u,s = u_s^H H_u^H = σ_s v_s^H ∈ C^(1×BS)

这一步把"用户有几根天线"折叠掉，之后的配对与预编码都在行向量上做—— SUS、SLNR 这些准则都假设每流一个行向量。

接收合并权是"单用户最优"选的，此刻还不知道会和谁配对。 严格最优要与配对联合优化，那是 NP 难，业界普遍接受这个次优。 如果要更接近现网，可以改成迭代：先配对 → 按配对结果重算合并权 → 再配对，迭代 2~3 轮。 要不要加这个迭代？

2

配对（选谁一起发）

默认 SUS（Yoo & Goldsmith 2006，半正交用户选择）。贪心：

S = {}；候选 T = 全部用户 循环直到 |S| = max_users 或 T 空： 1. 对每个 i ∈ T，把 h̃_i 投到 span{已选方向} 的正交补，得到 g_i 2. 选 argmax_i ( ‖g_i‖ · w_i ) ← w_i 是比例公平权重 3. 把它加进 S，其正交化方向加进基 4. 从 T 中剔除所有与它相关系数 > corr_threshold 的候选

复杂度 O(K²·max_users)。另外提供 greedy_sum_rate（每轮真算一遍 ZF 和速率，更准但每轮要 K 次求逆）、best_single（SU 对照）、 all（不筛选）。

三件事：(a) 配对在全带宽平均的等效信道上做（宽带配对）。 逐 RB 配对更优但要求逐 RB 反馈，现网基本不用——确认走宽带？
(b) corr_threshold 默认 0.5，这是常见取值不是标准值， 你们现场用多少？
(c) 配对用的是预编码侧的 CSI（真实基站看不到 h_true）。 用 h_true 配对等于偷看，MU 增益会偏乐观。

3

多用户预编码

把已选用户的等效行向量堆成 H̃ ∈ C^(N_stream×BS)：

ZF : W ∝ H̃^H (H̃ H̃^H)^(−1) RZF: W ∝ H̃^H (H̃ H̃^H + αI)^(−1)，α = N_stream·σ² / P MRT: W ∝ H̃^H

然后逐列归一到单位范数——W 只表示方向。 这与 Sionna 的 rzf_precoding_matrix 一致（它也是逐列归一）。

这里踩过一个坑，值得单独讲。 我最初把整个矩阵乘一个全局标量、 让 tr(WW^H) = P。看着合理，实际上 ZF 满足 H̃W = c·I—— 所有用户的接收电平被强行拉平，弱用户为了达到同一电平会吃掉大部分发射功率。 这就是信道求逆功控，公认的劣解。

症状极隐蔽：实测四个用户等效信道范数 12.0 / 11.7 / 10.7 / 7.2， 谱效却一模一样都是 11.482，Jain 公平度恒等于 1.000000—— 看起来像"MU 天生公平"。修正后变成 11.71 / 11.77 / 11.29 / 11.31。

4

功率分配

方向定了之后再决定每流分多少，总和归一到 P = 1：

equal : p_k = P / N_stream waterfilling: p_k = max(0, μ − σ²/g_k)，二分求 μ 使 Σp_k = P

总功率归一到 1，与 SU 侧口径严格一致。 Sionna 用的是 tr(GG^H) = K（每流各一份功率）， 照搬过来 MU 会比 SU 白拿 K 倍功率，"MU 增益"里一大半就成了功率增益， SU/MU 对比直接失效。这条我按"必须可比"处理了；如果你们现场的口径是 按流配功率，告诉我改。

5

逐用户 SINR

G = H̃_eval · W ← 注意用「评估」信道，不是预编码用的那个 SINR_k = p_k|G_kk|² / ( Σ_{j≠k} p_j|G_kj|² + σ² ) SE = mean_RB Σ_k log₂(1 + SINR_k)

理想 CSI + ZF 时 G 严格对角，用户间干扰为 0（测试里断言到 1e−12）。 CSI 有误差时非对角项就是残余干扰，结果里以 leakage_ratio 报出。

目前只算小区内的用户间干扰，没有把邻区干扰加进 σ²。 接上 linklevel.interference_covariance 就能补，而且和刚做的 IRC 是同一套东西。要不要现在就接？ 接了之后 MU 增益会明显下降—— 邻区干扰不会因为你做了 MU 就变小，但分母变大后相对增益被稀释。

二、需要你拍板的六点（汇总）

决策点我选了什么影响
接收合并权单用户 SVD，不与配对联合迭代次优但业界通行。加 2~3 轮迭代能再涨一点
配对粒度宽带（全带宽平均）逐 RB 更优但要逐 RB 反馈，现网基本不用
相关门限corr_threshold = 0.5常见取值，非标准值。想知道你们现场用多少
功率口径总功率 = 1，与 SU 一致照搬 Sionna 的每流一份会让 MU 白拿 K 倍
配对用的 CSI预编码侧的（不偷看 h_true）用真值配对会让 MU 增益偏乐观
邻区干扰暂未计入 SINR 分母接上会显著拉低 MU 增益，但更真实

三、还没做的

  • MU 的 MCS 选择与吞吐。 现在只到谱效，没接 linkadapt 那条 CQI→MCS→TBS 链。接上之后才能说"这个小区能扛多少 Mbps"。
  • 多流用户。 streams_per_user 参数在，但 > 1 时的配对准则 （用户内多流之间也会互相干扰）没有专门处理。
  • BD（块对角化）。 每用户多流时比 ZF 更合适，目前只有 ZF / RZF / MRT。
  • 比例公平的时间维。 weights 接口在，但没有跨时隙的历史速率 状态机——真正的 PF 调度需要它，而调度器按定位是不做的。 这条要不要破例？ 不做的话 weights 只能由调用方自己维护。
